1. Choix Technologiques Préliminaires

1.1 Pourquoi installer Java

Keycloak est un logiciel écrit en Java, développé principalement par Red Hat et basé sur le serveur d'applications Quarkus/WildFly. Pour s'exécuter sur un système d'exploitation, le code Java a besoin d'un environnement d'exécution appelé la JVM (Java Virtual Machine). Sans Java (openjdk), la VM Linux ne sait pas lire ni exécuter le binaire de Keycloak.

Principe retenu pour le socle d'exécution :
  • Keycloak = Application Java → nécessite la JVM (openjdk) pour tourner.
  • Flask = Application Python → nécessite l'interpréteur python3.
  • Nginx = Application C compilée en natif → s'exécute directement par le noyau Linux.

1.2 Nom du laboratoire

Le projet est identifié sous la nomenclature officielle : LAB-ZT-IAM-01 (Zero Trust & Identity Access Management — Niveau 1).

2. Choix de l'Image Système

L'installation repose sur la distribution Ubuntu Server 24.04 LTS (Fichier ISO : ubuntu-24.04-live-server-amd64.iso). Debian 12 représentait une alternative envisageable pour sa légèreté, mais Ubuntu Server offre une excellente stabilité de paquets récents.

Justification du choix Server : Absence totale d'interface graphique (GUI) consommatrice de mémoire RAM et de cycles CPU. L'ensemble des configurations s'effectue exclusivement en ligne de commande (CLI), en adéquation avec les standards de production cloud.

5. Déploiement de l'Infrastructure

5.1 Création du réseau KVM (zt-net)

Étape 1 — Définition du fichier XML :

cat <<EOF > zt-net.xml
<network>
  <name>zt-net</name>
  <forward mode='nat'/>
  <bridge name='virbr-zt0' status='isolated'/>
  <ip address='10.10.10.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='10.10.10.100' end='10.10.10.200'/>
      <host mac='52:54:00:00:10:10' name='reverse-proxy' ip='10.10.10.10'/>
      <host mac='52:54:00:00:10:20' name='iam-keycloak' ip='10.10.10.20'/>
      <host mac='52:54:00:00:10:30' name='app-flask' ip='10.10.10.30'/>
    </dhcp>
  </ip>
</network>
EOF

Étape 2 — Activation du réseau :

sudo virsh net-define zt-net.xml
sudo virsh net-start zt-net
sudo virsh net-autostart zt-net

Raison technique : Le mode NAT autorise les flux sortants pour les mises à jour système (apt update) tout en isolant le sous-réseau privé. Le couplage adresse MAC/IP garantit un adressage statique via le DHCP interne.

5.4 Pourquoi la désignation « Reverse Proxy » ?

Distinction fondamentale dans la modélisation des flux :

  • Proxy Classique (Forward Proxy) : Déployé côté client pour filtrer la navigation sortante et masquer l'origine des requêtes.
  • Reverse Proxy (Proxy Inverse) : Placé en amont des serveurs pour agir comme composant frontal unique (Policy Enforcement Point). Il protège l'infrastructure interne, masque la topologie du réseau, gère la terminaison TLS et prévient l'exposition directe des micro-services.

5.5 Processus d'attribution IP (Négociation DORA & Reservation MAC)

L'attribution déterministe de l'IP dès le démarrage repose sur la chaîne d'interaction suivante :

  1. Fichier XML KVM : L'association 52:54:00:00:10:10 ➔ 10.10.10.10 est inscrite dans le service dnsmasq.
  2. virt-install : L'option mac=... fixe l'adresse physique de la carte virtuelle vnet.
  3. Négociation DORA : La VM émet un Discover avec sa MAC fixe, le DHCP KVM renvoie une Offer pour 10.10.10.10, suivie de la Request et du Acknowledge.
  4. DNS Local : dnsmasq enregistre dynamiquement la résolution reverse-proxy vers 10.10.10.10.

8.2 Code Source de l'API avec Validation JWT Autonome (app.py)

import jwt
import requests
from flask import Flask, jsonify, request

app = Flask(__name__)

KEYCLOAK_CERTS_URL = "http://10.10.10.20:8080/realms/zerotrust-realm/protocol/openid-connect/certs"

def get_public_key(token):
    try:
        headers = jwt.get_unverified_header(token)
        kid = headers.get("kid")
        
        res = requests.get(KEYCLOAK_CERTS_URL, timeout=5)
        keys = res.json().get("keys", [])
        
        key_data = next((k for k in keys if k.get("kid") == kid), None)
        if not key_data:
            return None
            
        return jwt.algorithms.RSAAlgorithm.from_jwk(key_data)
    except Exception as e:
        print(f"Erreur lors de la récupération de la clé : {e}")
        return None

@app.route("/api/secure", methods=["GET"])
def secure_api():
    auth_header = request.headers.get("Authorization")
    
    if not auth_header or not auth_header.startswith("Bearer "):
        return jsonify({"status": "Erreur", "message": "Accès refusé : Aucun Token Bearer fourni"}), 401

    token = auth_header.split(" ")[1]

    if token == "null" or not token or len(token.split(".")) != 3:
        return jsonify({"status": "Erreur", "message": "Token invalide ou malformé"}), 401

    public_key = get_public_key(token)
    if not public_key:
        return jsonify({"status": "Erreur", "message": "Impossible de vérifier la clé publique de Keycloak"}), 401

    try:
        payload = jwt.decode(
            token,
            key=public_key,
            algorithms=["RS256"],
            options={"verify_aud": False}
        )
        
        username = payload.get("preferred_username", "Utilisateur inconnu")
        return jsonify({
            "status": "Succès Zero Trust",
            "message": f"Bienvenue {username} ! Votre token JWT est valide.",
            "user_info": {
                "username": username,
                "email": payload.get("email"),
                "roles": payload.get("realm_access", {}).get("roles", [])
            }
        }), 200

    except jwt.ExpiredSignatureError:
        return jsonify({"status": "Erreur", "message": "Accès refusé : Le Token JWT a expiré"}), 401
    except jwt.InvalidTokenError as e:
        return jsonify({"status": "Erreur", "message": f"Accès refusé : Token invalide ({str(e)})"}), 401

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)

Lancement de l'application : python3 app.py

9. Configuration de la VM 1 (reverse-proxy)

9.1 Installation et Configuration de Nginx

ssh adminuser@10.10.10.10

Fichier /etc/nginx/sites-available/default :

server {
    listen 80 default_server;
    listen [::]:80 default_server;

    server_name _;

    location /api/ {
        proxy_pass http://10.10.10.30:5000/api/;
        
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Authorization $http_authorization;
    }

    location / {
        return 200 'Point d\'entree Reverse Proxy Nginx - Zero Trust Lab\n';
        add_header Content-Type text/plain;
    }
}
sudo nginx -t
sudo systemctl restart nginx

10. Analyse des Incidents & Troubleshooting

  • Mot de passe temporaire Keycloak : L'attribut Temporary: ON dans la fiche de l'utilisateur bloque le flux Direct Access Grants (erreur 400 Bad Request). Doit être positionné sur OFF.
  • Required Actions Realm : Désactivation obligatoire de la directive Verify Profile dans la section Authentication > Required Actions pour autoriser la délivrance immédiate de jetons d'accès via l'API.
  • Dépendances Cryptographiques Python : L'absence du paquet cryptography dans l'environnement virtuel empêche le décodage des paires de clés asymétriques RSA. L'installation via pip install cryptography résout le blocage.

12. Conclusion

L'architecture du laboratoire LAB-ZT-IAM-01 est totalement opérationnelle et conforme aux exigences Zero Trust de Niveau 1 :

  1. Chaque flux passe obligatoirement par le Reverse Proxy Nginx (10.10.10.10).
  2. L'authentification est déléguée au serveur IAM centralisé Keycloak (10.10.10.20).
  3. L'API applicative Flask (10.10.10.30) valide l'intégrité et la signature du jeton OIDC/JWT en toute autonomie (stateless) via JWKS avant d'accorder l'accès aux ressources.
