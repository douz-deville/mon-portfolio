WordPress Multi-AZ Hautement Disponible sur AWS

Ce guide détaille l'intégralité du déploiement réalisé lors de la Semaine 1 du Bootcamp AWS CloudOps Essentials : la conception de l'architecture, l'installation, la configuration réseau, le découplage des données, l'industrialisation par image système et Auto Scaling, et les procédures de validation par test de panne (Build & Break).

1. Architecture globale et matrice réseau

L'objectif de cette infrastructure est de garantir un fonctionnement sans interruption de service (Zero-Downtime), un découplage strict entre la couche applicative stateless et la couche de données stateful, ainsi qu'un haut niveau de sécurité réseau grâce au masquage des serveurs applicatifs dans des sous-réseaux privés.

3. Déploiement pas à pas

Phase 1 — Infrastructure réseau & VPC

J'ai commencé par poser le socle réseau avant de déployer le moindre serveur.

  1. Création du VPC : dans VPC > Your VPCs > Create VPC, j'ai nommé le VPC WordPress-VPC avec un bloc IPv4 10.0.0.0/16.
  2. Création des sous-réseaux : j'ai créé Pub-Subnet-AZ1 (10.0.1.0/24) et Priv-Subnet-AZ1 (10.0.2.0/24) dans eu-north-1a, puis Pub-Subnet-AZ2 (10.0.3.0/24) et Priv-Subnet-AZ2 (10.0.4.0/24) dans eu-north-1b.
  3. Routage Internet : j'ai créé une Internet Gateway (WordPress-IGW), je l'ai attachée au VPC, puis j'ai créé une table de routage publique avec une route 0.0.0.0/0 vers cette passerelle, associée aux deux sous-réseaux publics.
  4. DB Subnet Group : dans RDS > Subnet groups, j'ai créé wordpress-db-subnet-group en sélectionnant explicitement les deux zones eu-north-1a et eu-north-1b, avec les sous-réseaux privés 10.0.2.0/24 et 10.0.4.0/24.

Phase 2 — Base de données RDS MySQL Multi-AZ

  1. Security Group BDD : j'ai créé WordPress-DB-SG, rattaché à WordPress-VPC.
  2. Création de la base : moteur MySQL 8.0+, instance db.t3.micro, option Multi-AZ DB instance activée, identifiant wordpress-db, utilisateur admin. J'ai placé la base dans WordPress-VPC via wordpress-db-subnet-group, accès public désactivé, Security Group WordPress-DB-SG, et une base initiale nommée wordpress.
  3. Récupération de l'endpoint : une fois le statut passé à Available, j'ai copié l'endpoint de connexion (de la forme wordpress-db.c1e48mc2w244.eu-north-1.rds.amazonaws.com) pour l'utiliser lors de l'installation de WordPress.

Phase 3 — Serveur web initial & configuration WordPress

J'ai lancé une première instance EC2 (WordPress-Web-Server, AMI Amazon Linux 2023, type t3.micro) dans Pub-Subnet-AZ1 avec IP publique activée, rattachée au Security Group WordPress-Web-SG. Je m'y suis connecté via EC2 Instance Connect pour installer la pile LAMP et déployer WordPress :

# Update système et installation des paquets applicatifs
sudo dnf update -y
sudo dnf install -y httpd php php-mysqli mariadb105

# Activation du service web
sudo systemctl start httpd
sudo systemctl enable httpd

# Téléchargement et déploiement de WordPress
cd /var/www/html
sudo wget https://wordpress.org/latest.tar.gz
sudo tar -xzf latest.tar.gz
sudo cp -r wordpress/* .
sudo rm -rf wordpress latest.tar.gz

# Attribution des droits sur le dossier web
sudo chown -R apache:apache /var/www/html
sudo chmod -R 755 /var/www/html

J'ai ensuite ouvert le flux réseau manquant entre les deux couches : dans WordPress-DB-SG, j'ai ajouté une règle entrante MYSQL/Aurora (3306) avec pour source le Security Group WordPress-Web-SG — sans cette règle, le pare-feu virtuel bloque tout accès du serveur web vers la base.

J'ai terminé l'installation via l'assistant web de WordPress (http://<IP_PUBLIQUE_EC2>), en renseignant le nom de base wordpress, l'utilisateur admin, l'endpoint RDS comme hôte de base de données, et le préfixe de table wp_, avant de créer le compte administrateur du site.

Phase 4 — Haute disponibilité (AMI, ALB & Auto Scaling)

  1. Création de l'AMI : à partir de WordPress-Web-Server déjà configuré, j'ai créé une image WordPress-AMI-v1, qui sert ensuite de modèle reproductible pour toute nouvelle instance.
  2. Target Group : j'ai créé WordPress-TG (type Instances, protocole HTTP:80, health check sur /).
  3. Application Load Balancer : j'ai créé WordPress-ALB en mode Internet-facing, réparti sur les deux sous-réseaux publics, avec un listener HTTP:80 redirigeant vers WordPress-TG.
  4. Launch Template : j'ai créé WordPress-LT à partir de l'AMI WordPress-AMI-v1, type t3.micro, Security Group WordPress-Web-SG.
  5. Auto Scaling Group : j'ai déployé WordPress-ASG à partir de ce Launch Template, réparti sur les deux sous-réseaux privés, rattaché au Target Group WordPress-TG, avec une capacité désirée de 2 instances (min 2, max 4).
  6. Bascule du DNS du site : dans l'administration WordPress, j'ai remplacé l'ancienne IP publique par le nom DNS de l'ALB (WordPress-ALB-xxx.eu-north-1.elb.amazonaws.com), afin que le site référence désormais le point d'entrée résilient plutôt qu'un serveur unique.

4. Procédure de validation « Build & Break »

Plutôt que de me contenter d'une architecture qui semble correcte sur le papier, j'ai voulu vérifier concrètement sa capacité à tolérer une perte matérielle soudaine.

[ Action User ] : Suppression manuelle d'une instance EC2 active dans EC2 Console
       │
       ▼
[ ALB Health Check ] : Échec de la sonde HTTP sur l'instance détruite
       │
       ▼
[ ALB Routing ] : Redirection à 100% du trafic vers l'instance restante (0s coupure)
       │
       ▼
[ ASG Metrics ] : Détection de l'écart de capacité (1 instance active / 2 désirées)
       │
       ▼
[ ASG Auto-Healing ] : Lancement automatique d'une nouvelle instance depuis WordPress-LT

Résultats observés

  • Suppression : j'ai forcé la terminaison de l'instance i-0123456789101112a.
  • Disponibilité web : le site est resté continuellement accessible via l'URL de l'ALB, sans générer d'erreur HTTP 502/503.
  • Réparation automatique : l'Auto Scaling Group a généré un événement Launching a new EC2 instance et rétabli la cible de 2 instances en moins de 120 secondes.

5. Journal d'incidents et résolutions

Quatre blocages réels ont jalonné ce déploiement. Je les détaille tels que rencontrés, avec le diagnostic et la correction appliquée.

Incident 1 — Incompatibilité de couverture AZ du DB Subnet Group

Symptôme : « The DB subnet group doesn't meet Availability Zone coverage requirement. Add subnets to cover at least 2 AZs. »

Cause : les sous-réseaux sélectionnés appartenaient tous à la même zone de disponibilité (eu-north-1a).

Correction : j'ai recréé le second sous-réseau privé spécifiquement sur eu-north-1b, puis sélectionné explicitement deux zones distinctes dans la configuration du Subnet Group.

Incident 2 — Absence de capacité IP dans la zone eu-north-1c

Symptôme : « You can't create a db.t4g.micro instance because there are no subnets with available IP addresses in eu-north-1c. »

Cause : RDS tentait de provisionner une réplique dans une troisième zone (eu-north-1c) non configurée dans mon VPC.

Correction : j'ai retiré eu-north-1c du DB Subnet Group pour contraindre le périmètre de haute disponibilité aux seules zones eu-north-1a et eu-north-1b réellement configurées.

Incident 3 — Erreur « Gateway Timeout » (HTTP 504) lors de l'installation WordPress

Symptôme : l'assistant WordPress s'exécutait dans le vide puis échouait par dépassement de délai d'attente.

Cause : le Security Group WordPress-DB-SG ne possédait aucune règle entrante — le pare-feu virtuel bloquait tout le trafic sur le port 3306.

Correction : j'ai ajouté la règle entrante MYSQL/Aurora (3306) avec pour source le Security Group WordPress-Web-SG.

Incident 4 — Erreur « 503 Service Temporarily Unavailable » sur l'ALB

Symptôme : l'accès au site via le DNS de l'ALB renvoyait une erreur 503.

Cause : le Target Group de l'ALB n'avait aucune cible enregistrée, les instances étant encore en cours d'initialisation par l'Auto Scaling Group.

Correction : j'ai vérifié l'association explicite du Target Group WordPress-TG dans la configuration de l'Auto Scaling Group, puis attendu le délai de grâce du health check avant que les instances ne soient déclarées saines.

Conclusion

Cette infrastructure valide, de bout en bout, les trois piliers d'une architecture hautement disponible : l'absence de point d'entrée unique côté réseau (ALB réparti sur deux zones), l'absence de point de calcul unique côté application (Auto Scaling Group auto-réparable), et l'absence de point de persistance unique côté données (RDS Multi-AZ répliqué). Le test de panne « Build & Break » n'était pas une formalité : c'est la preuve que cette résilience fonctionne réellement, pas seulement sur le schéma d'architecture.
