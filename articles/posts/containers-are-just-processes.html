CONTAINER SECURITY — PARTIE 1 Publié le 15 Octobre 2026

Les conteneurs ne sont que des processus

Comprendre la réalité technique d'un conteneur Linux pour mieux appréhender ses mécanismes d'isolement et ses vecteurs d'attaque.

Container Security Docker Linux Sécurité

Dans cette série, je veux comprendre comment les conteneurs fonctionnent vraiment, et surtout comment ils utilisent des fonctions de Linux pour s'isoler les uns des autres. Pourquoi ? Parce qu'on ne peut pas bien protéger ce qu'on ne comprend pas. Si je sais comment un conteneur est construit, je sais aussi où il peut casser.

Ce premier article ne traite qu'une seule idée. Elle est simple à dire, mais elle change toute la façon de penser la sécurité des conteneurs :

Un conteneur est un processus Linux normal, lancé avec quelques restrictions autour de lui.

1. Pourquoi cette idée est si importante

Beaucoup de gens imaginent un conteneur comme une petite machine virtuelle : un mini-ordinateur avec son propre système, enfermé dans une boîte. Ce n'est pas vrai. Et cette mauvaise image mène à de mauvaises décisions de sécurité.

Si je crois qu'un conteneur est une boîte étanche, je vais lui faire confiance trop vite. Si je comprends que c'est un processus de l'hôte avec des limites ajoutées par le noyau, je vais me poser les bonnes questions :

  • Quelles limites exactement ? Qui les a posées ? Peuvent-elles être retirées ?
  • Qui, sur l'hôte, peut voir ce qui se passe dans le conteneur ?
  • Que se passe-t-il si le noyau lui-même a une faille ?

Tout le reste de la série répond à ces questions, une par une.

2. Ce qu'un conteneur n'est pas : une machine virtuelle

Voici les deux modèles côte à côte.

        MACHINE VIRTUELLE                           CONTENEURS

┌──────────────┐ ┌──────────────┐        ┌──────────────┐ ┌──────────────┐
│    App A     │ │    App B     │        │    App A     │ │    App B     │
│ Bibliothèques│ │ Bibliothèques│        │ Bibliothèques│ │ Bibliothèques│
│ Noyau invité │ │ Noyau invité │        └──────┬───────┘ └──────┬───────┘
└──────┬───────┘ └──────┬───────┘               │                │
       │                │                ┌──────┴────────────────┴──────┐
┌──────┴────────────────┴──────┐         │   Noyau Linux de l'hôte      │
│          Hyperviseur         │         │   (UN SEUL, partagé)         │
└──────────────┬───────────────┘         └──────────────┬───────────────┘
               │                                        │
          Matériel (CPU, RAM)                      Matériel (CPU, RAM)

La différence la plus importante est en bas : une machine virtuelle a son propre noyau, un conteneur utilise le noyau de l'hôte.

Élément Machine virtuelle Conteneur
Noyau Un noyau par VM (le noyau « invité ») Un seul noyau, celui de l'hôte, partagé
Ce qui isole L'hyperviseur et le matériel (virtualisation) Des fonctions du noyau Linux
Démarrage Démarre tout un système (secondes à minutes) Lance un processus (très rapide)
Poids Une image complète de système (plusieurs Go) Seulement l'application et ses fichiers
Système possible Windows, Linux, etc. Même noyau que l'hôte (Linux pour conteneurs Linux)
Si le noyau a une faille La faille touche seulement cette VM La faille touche l'hôte et tous les conteneurs

Le dernier point est celui qui compte le plus pour la sécurité.

3. Rappel : qu'est-ce qu'un processus Linux ?

Quand on lance un programme sur Linux, le noyau crée un processus. C'est un objet que le noyau suit avec beaucoup d'informations :

Information À quoi ça sert
PID Le numéro unique du processus
Parent (PPID) Le processus qui l'a lancé
UID / GID L'utilisateur et le groupe au nom desquels il tourne
Mémoire Son espace mémoire privé
Fichiers ouverts La liste de ses descripteurs de fichiers
Répertoire racine Ce qu'il voit comme /
Namespaces Ce qu'il voit du système (processus, réseau, points de montage…)
Cgroup Combien de CPU et de mémoire il peut utiliser
Capabilities Les droits spéciaux qu'il possède
Filtre seccomp Les appels système qu'il a le droit de faire
Étiquette de sécurité Son profil AppArmor ou SELinux

Retenons cette liste : les namespaces, cgroups, capabilities, seccomp et l'étiquette de sécurité sont exactement ce qu'un moteur de conteneurs règle pour fabriquer un conteneur.

Le système de fichiers /proc

Le noyau expose toutes ces informations dans un dossier spécial : /proc. Pour chaque processus, un sous-dossier /proc/<PID>/ contient des fichiers qui décrivent ce processus :

Chemin Contenu
/proc/<PID>/root Le répertoire racine du processus (ce qu'il voit comme /)
/proc/<PID>/cwd Son répertoire courant
/proc/<PID>/exe Le programme qu'il exécute
/proc/<PID>/environ Ses variables d'environnement
/proc/<PID>/cgroup Son groupe de contrôle de ressources
/proc/<PID>/ns/ Les namespaces auxquels il appartient
/proc/<PID>/fd/ Ses fichiers ouverts

4. La démonstration pas à pas

Avant de commencer : Il faut un hôte Linux. Sur Windows ou macOS, Docker Desktop fait tourner les conteneurs dans une VM cachée et les commandes ne verraient pas directement les processus.

Étape 1 : chercher nginx sur l'hôte

ps -fC nginx

Résultat : rien. Aucun serveur nginx ne tourne sur cette machine.

Étape 2 : lancer un conteneur nginx

docker run -d --name webserver nginx

Étape 3 : regarder la liste des processus de l'hôte

ps -fC nginx

Résultat :

UID         PID    PPID  C STIME TTY          TIME CMD
root       46727  46705  0 10:42 ?        00:00:00 nginx: master process nginx -g daemon off;
101        46783  46727  0 10:42 ?        00:00:00 nginx: worker process
101        46784  46727  0 10:42 ?        00:00:00 nginx: worker process

L'hôte voit des processus nginx normaux. Pour lui, c'est comme si nginx était installé en local. Le processus principal a le PID 46727.

Étape 4 : créer un fichier à l'intérieur du conteneur

docker exec webserver touch /mynewfile

Étape 5 : retrouver ce fichier depuis l'hôte, sans Docker

sudo ls /proc/46727/root
bin  boot  dev  docker-entrypoint.d  docker-entrypoint.sh  etc  home  lib  lib64
media  mnt  mynewfile  opt  proc  root  run  sbin  srv  sys  tmp  usr  var

On voit le fichier mynewfile accessible directement depuis l'hôte avec les outils standards.

5. Pour aller plus loin : cinq expériences à faire

a) Trouver le PID automatiquement

docker inspect -f '{{.State.Pid}}' webserver

b) Voir la liste des processus du conteneur

docker top webserver

c) Regarder les namespaces du processus

sudo ls -l /proc/46727/ns

d) Regarder le cgroup

cat /proc/46727/cgroup

e) Retrouver le fichier sur le disque de l'hôte

sudo find /var/lib/docker/overlay2 -name mynewfile 2>/dev/null

6. Deux numéros pour un même processus

Dans le conteneur, nginx croit être le processus numéro 1. Sur l'hôte, il porte le numéro 46727. Le noyau lui attribue un numéro dans chaque espace de numéros (PID namespace).

7. Qui fabrique le conteneur, alors ?

Le noyau Linux n'a pas d'objet appelé « conteneur ». C'est une convention : un moteur de conteneurs règle plusieurs fonctions du noyau sur un processus ordinaire.

docker (client)
      │
      ▼
dockerd (le démon Docker)
      │
      ▼
containerd (gère le cycle de vie)
      │
      ▼
containerd-shim (reste en vie à côté du conteneur)
      │
      ▼
runc (règle le noyau, lance le processus et s'arrête)
      │
      ▼
le processus nginx  ←  c'est lui, le « conteneur »
Fonction du noyau Rôle
Namespaces Isole la vue (processus, réseau, fichiers montés…)
Cgroups Limite la consommation (CPU, mémoire…)
Capabilities Limite les privilèges spécifiques
Seccomp Filtre les appels système autorisés
AppArmor / SELinux Applique les règles d'accès obligatoires
OverlayFS Gère le système de fichiers en couches

8. Ce que cela change pour la sécurité

a) Le noyau est partagé : surface d'attaque commune

Si le noyau Linux a une faille (ex: Dirty COW CVE-2016-5195 ou CVE-2019-5736 sur runc), un conteneur peut potentiellement compromettre l'hôte entier.

b) L'hôte voit tout

Un administrateur root sur l'hôte peut lire la mémoire et les variables d'environnement de n'importe quel conteneur :

sudo cat /proc/46727/environ | tr '\0' '\n'

c) Qui parle à Docker est root de fait

Accéder au démon Docker ou au groupe docker équivaut à un accès root sur l'hôte.

d) Le mode --privileged

Ce mode désactive la majorité des protections du noyau et doit être évité.

9. Idées fausses fréquentes

Idée fausse Réalité
« Un conteneur est une petite VM » C'est un processus isolé de l'hôte.
« Il y a un noyau par conteneur » Le noyau est unique et partagé avec l'hôte.
« Ce qui est dedans est caché de l'hôte » root sur l'hôte lit tout via /proc.
« root du conteneur est inoffensif » Sans user namespaces, l'UID 0 du conteneur est l'UID 0 de l'hôte.

Conclusion

Un conteneur n'est pas une boîte magique : c'est un processus Linux ordinaire configuré pour voir moins de choses et consommer des ressources contrôlées. Dans le prochain article, nous aborderons la première brique d'isolement : les namespaces.
