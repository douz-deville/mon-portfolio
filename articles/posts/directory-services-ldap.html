Où vivent les identités — Active Directory, LDAP et les services d'annuaire

Déconstruire les confusions courantes entre la source de vérité, le service d'annuaire et le protocole d'interrogation.

IAM Active Directory LDAP

Où penses-tu que les identités sont stockées ?

Pose-toi la question avant de lire la suite : dans une entreprise, où vivent réellement les comptes utilisateurs ? Une base de données ? Un annuaire ? Active Directory ? LDAP ? Le cloud ?

La plupart de ces réponses sont correctes selon le contexte — sauf une, qui semble intuitive mais qui ne l'est pas : LDAP. Certainement pas LDAP... ou est-ce que ça l'est ? La réponse, contre-intuitive pour beaucoup, est non : LDAP ne stocke rien. C'est un protocole d'interrogation, pas un entrepôt de données. La confusion est si répandue qu'elle mérite d'être déconstruite avant d'aller plus loin — c'est tout l'objet de cet article.

Un maillon manquant dans l'article précédent

Le premier article de cette série a décrit les trois domaines de l'IAM — gouvernance, gestion des accès, comptes privilégiés — sans s'attarder sur une question pourtant préalable à tous les trois : où les identités sont-elles réellement stockées ? Un outil comme SailPoint, Okta ou Keycloak ne fabrique pas les identités qu'il gère — il s'appuie sur une source qui les contient déjà.

Qu'est-ce qu'Active Directory ?

Active Directory (AD) est un service d'annuaire développé par Microsoft, introduit à la fin des années 1990 avec Windows NT puis Windows 2000 Server, devenu depuis le standard de fait dans la majorité des entreprises équipées d'un environnement Windows. Concrètement, AD stocke des objets — utilisateurs, machines, imprimantes, groupes, comptes de service — chacun avec un ensemble d'attributs, organisés pour être recherchés, modifiés et supprimés efficacement.

Ce qui rend AD central n'est pas son ancienneté en soi, mais le rôle qu'il occupe structurellement : c'est souvent la toute première brique posée dans une organisation, celle à laquelle tout le reste — authentification, outils IAM, système RH — vient se connecter. C'est en ce sens qu'on le désigne comme source de vérité : ce n'est pas qu'AD soit infaillible, c'est que c'est l'endroit où l'identité existe en premier, avant d'être consommée ailleurs.

Cette architecture repose sur quelques composants qu'il vaut la peine de distinguer :

  • les contrôleurs de domaine (Domain Controllers) : les serveurs qui hébergent réellement les données et répondent aux requêtes,
  • une structure arborescente, avec des unités organisationnelles (OU) qui regroupent les objets par département ou par fonction,
  • des stratégies de groupe (Group Policy Objects), qui appliquent des règles centralisées à ces regroupements.

Le problème concret que LDAP résout

Imagine un système qui a besoin de faire l'une de ces choses : effectuer une recherche sur un utilisateur, authentifier un utilisateur, ou gérer un utilisateur (le créer, le modifier). Dans les trois cas, la question est la même : où cette information vit-elle réellement ? La réponse, on vient de le voir, est l'annuaire — Active Directory dans le cas le plus courant.

Mais ça soulève une seconde question, plus pratique : comment ce système parle-t-il concrètement à AD ? AD n'expose pas une API REST universelle que n'importe quel outil peut appeler nativement. C'est précisément là que LDAP (Lightweight Directory Access Protocol) entre en jeu : c'est le canal de communication standardisé qui permet à un système tiers d'interroger, d'authentifier contre, ou de modifier les données hébergées dans AD — ou dans n'importe quel autre annuaire qui implémente ce même protocole ouvert (OpenLDAP, FreeIPA).

Une confusion fréquente mérite d'être clarifiée à ce stade : LDAP n'est pas une fonctionnalité propre à Active Directory, ni un produit Microsoft. C'est un protocole ouvert, indépendant de tout fournisseur — ce qui explique pourquoi la question posée en ouverture de cet article ("LDAP stocke-t-il des identités ?") a une réponse non intuitive : LDAP est le messager, pas l'entrepôt.

Comment LDAP organise les données : le DIT

LDAP structure les données qu'il interroge selon une hiérarchie appelée DIT (Directory Information Tree) — un arbre, pas une table. Chaque nœud, appelé entrée, représente un objet : un utilisateur, un groupe, une machine. 

dc=exemple,dc=com
├── ou=utilisateurs
│    ├── uid=alice
│    └── uid=bob
└── ou=groupes
    ├── cn=admins
    └── cn=devs

Trois notions structurent cet arbre :

  • Le DN (Distinguished Name) identifie de façon unique une entrée par son chemin complet dans l'arbre — par exemple uid=alice,ou=utilisateurs,dc=exemple,dc=com. C'est l'équivalent, pour LDAP, d'un chemin de fichier complet plutôt qu'un simple nom.
  • Les attributs sont des paires clé-valeur portées par chaque entrée (mail: alice@exemple.com, cn: Alice Doe).
  • L'objectClass définit quelle structure d'attributs une entrée doit respecter — un utilisateur et une imprimante n'ont pas le même schéma d'attributs obligatoires.

Bind et Search : les deux opérations qui comptent vraiment

LDAP expose plusieurs opérations, mais deux dominent l'usage réel dans une architecture d'identité :

Bind, l'opération d'authentification : elle consiste à tenter une connexion avec un DN et un mot de passe donnés. Si l'annuaire accepte, les identifiants sont valides ; sinon, non. C'est délibérément binaire — LDAP répond uniquement à la question "ces identifiants sont-ils corrects", il ne crée ni session ni jeton derrière cette réponse.

Search, l'opération de loin la plus fréquente en pratique : interroger l'annuaire à partir d'une base (à quel endroit de l'arbre chercher) et d'un filtre (quel critère), pour récupérer les attributs d'une ou plusieurs entrées.

Le déroulé typique d'une authentification applicative combine les deux : l'application effectue d'abord une recherche pour retrouver le DN correspondant à un identifiant fourni par l'utilisateur, puis tente un bind avec ce DN et le mot de passe saisi. LDAP ne maintient aucun état de session après ce bind — à l'application de gérer ce qui se passe ensuite, ce qui explique pourquoi LDAP se retrouve presque toujours derrière une couche supplémentaire, pas exposed directement.

Le pont concret entre AD et Keycloak

Reprenons l'exemple du départ, appliqué à Keycloak. Une organisation a déjà tous ses utilisateurs dans Active Directory, mais veut ajouter par-dessus les protocoles modernes de délégation décrits dans les articles précédents (OAuth2, OIDC). Elle n'a pas besoin de dupliquer sa base d'utilisateurs dans Keycloak — c'est là que sert la fédération LDAP, une fonctionnalité native de Keycloak.

Concrètement, l'administrateur configure dans Keycloak un fournisseur de type "LDAP" (sous User Federation), avec quelques paramètres clés :

  • l'URL de connexion vers le contrôleur de domaine AD (ldap:// ou ldaps:// pour une connexion chiffrée),
  • le Bind DN et son mot de passe : un compte de service dédié, avec juste assez de droits pour interroger l'annuaire — jamais un compte administrateur complet,
  • les Users DN : la portion de l'arbre où chercher les utilisateurs (par exemple ou=utilisateurs,dc=exemple,dc=com),
  • un filtre de recherche qui précise quels objets AD compter comme utilisateurs valides.

Une fois configuré, le flux d'authentification suit exactement le déroulé bind/search décrit plus haut, mais orchestré par Keycloak plutôt que par l'application elle-même : un utilisateur saisit ses identifiants sur l'écran de connexion Keycloak → Keycloak effectue une recherche LDAP pour localiser le DN de cet utilisateur dans AD → Keycloak tente un bind avec ce DN et le mot de passe saisi → si le bind réussit, Keycloak considère l'utilisateur authentifié et prend le relais pour tout ce que les articles précédents ont décrit : émission du jeton, gestion de sa durée de vie, claims.

L'intérêt structurel de ce montage : AD reste l'unique source de vérité pour l'identité et le mot de passe — rien n'est dupliqué ni resynchronisé manuellement — pendant que Keycloak ajoute par-dessus tout ce qu'AD ne sait pas faire nativement : émission de JWT, SSO vers des applications SaaS, MFA adaptatif.

Pourquoi LDAP est pensé pour la lecture, pas pour l'écriture

LDAP est architecturalement optimisé pour des lectures rapides et fréquentes, pas pour des écritures massives ou transactionnelles :

  • les attributs les plus consultés (uid, mail) sont indexés, ce qui rend leur recherche très rapide,
  • les recherches sont scopées à une portion précise de l'arbre plutôt qu'à l'ensemble de l'annuaire, ce qui réduit le coût de chaque requête,
  • le modèle de réplication privilégie de nombreuses répliques en lecture seule pour quelques nœuds maîtres en écriture — cohérent avec une charge dominée par des milliers de tentatives de connexion, contre relativement peu de créations ou modifications de comptes,
  • un schéma strict impose une structure prévisible, ce qui évite le coût de jointures complexes qu'une base relationnelle devrait gérer pour un usage équivalent.

Cette asymétrie a une contrepartie : LDAP gère mal les écritures fréquentes et les transactions complexes. Ce n'est pas une faiblesse de conception, c'est une spécialisation — pensé pour l'identité, consultée en permanence, modifiée rarement.

Au-delà de l'authentification applicative : où LDAP intervient ailleurs

LDAP n'est pas cantonné aux applications web. Il est invoqué en silence dans une bonne partie de l'infrastructure d'entreprise : le WiFi sécurisé (802.1X, via un serveur RADIUS qui interroge l'annuaire en coulisses), les connexions VPN, l'ouverture de session sur des serveurs Linux (via SSSD ou PAM-LDAP), la recherche de contacts dans un client de messagerie, ou même l'authentification à l'impression sur certaines imprimantes réseau. Dans chaque cas, le même schéma se répète : un système qui n'a, autrement, aucune raison de faire confiance à l'utilisateur interroge l'annuaire central via LDAP pour vérifier son identité.

Ce que les outils IAM modernes ajoutent, et ce qu'ils ne remplacent pas

Une question légitime : si Active Directory gère déjà les utilisateurs et l'authentification, pourquoi investir dans des outils IAM supplémentaires ?

Élément Approche historique (AD/LDAP seuls) Outils IAM modernes
Gestion des rôles Groupes gérés manuellement RBAC automatisé, revues d'accès périodiques
Périmètre Réseau interne, on-premise Cloud, SaaS, multi-environnements
Authentification Bind LDAP direct SSO, MFA, SAML, OpenID Connect
Session / jeton Aucun — LDAP répond juste "valide ou non" Sessions gérées, tokens signés (JWT)
Gouvernance Journaux à interpréter manuellement Audits automatisés, certifications d'accès

La ligne "session / jeton" est la plus révélatrice : LDAP ne gère ni l'un ni l'autre. C'est exactement le vide que la fédération Keycloak, décrite plus haut, vient combler.

Ce que cet article laisse ouvert

Un annuaire répond à "où l'identité est stockée", LDAP répond à "comment un système l'interroge et l'authentifie localement". Mais aucun des deux ne répond à une question qui devient centrale dès qu'une organisation utilise plusieurs systèmes indépendants : comment un utilisateur authentifié accède-t-il, sans se reconnecter, à une application qui ne partage pas cet annuaire — chez un autre fournisseur, ou dans une autre organisation ? C'est le rôle de la fédération d'identité inter-organisations, distincte de la fédération LDAP décrite ici, et qui fera l'objet d'un prochain article.
