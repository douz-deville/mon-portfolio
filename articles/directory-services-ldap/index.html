LDAP Active Directory IAM

Arborescence, opérations et performances dans les annuaires LDAP

Structure fondamentales de l'arbre LDAP

Trois notions structurent cet arbre :

  • Le DN (Distinguished Name) identifie de façon unique une entrée par son chemin complet dans l'arbre — par exemple uid=alice,ou=utilisateurs,dc=exemple,dc=com. C'est l'équivalent, pour LDAP, d'un chemin de fichier complet plutôt qu'un simple nom.
  • Les attributs sont des paires clé-valeur portées par chaque entrée (mail: alice@exemple.com, cn: Alice Doe).
  • L'objectClass définit quelle structure d'attributs une entrée doit respecter — un utilisateur et une imprimante n'ont pas le même schéma d'attributs obligatoires.

Bind et Search : les deux opérations qui comptent vraiment

LDAP expose plusieurs opérations, mais deux dominent l'usage réel dans une architecture d'identité :

Bind, l'opération d'authentification : elle consiste à tenter une connexion avec un DN et un mot de passe donnés. Si l'annuaire accepte, les identifiants sont valides ; sinon, non. C'est délibérément binaire — LDAP répond uniquement à la question "ces identifiants sont-ils corrects", il ne crée ni session ni jeton derrière cette réponse.

Search, l'opération de loin la plus fréquente en pratique : interroger l'annuaire à partir d'une base (à quel endroit de l'arbre chercher) et d'un filtre (quel critère), pour récupérer les attributs d'une ou plusieurs entrées — retrouver l'adresse e-mail d'un utilisateur, lister les membres d'un groupe, etc.

Le déroulé typique d'une authentification applicative combine les deux : l'application effectue d'abord une recherche pour retrouver le DN correspondant à un identifiant fourni par l'utilisateur, puis tente un bind avec ce DN et le mot de passe saisi. LDAP ne maintient aucun état de session après ce bind — à l'application de gérer ce qui se passe ensuite, ce qui explique pourquoi LDAP se retrouve presque toujours derrière une couche supplémentaire, pas exposé directement.

Pourquoi LDAP est pensé pour la lecture, pas pour l'écriture

Un point souvent implicite mais qui vaut la peine d'être rendu explicite : LDAP est architecturalement optimisé pour des lectures rapides et fréquentes, pas pour des écritures massives ou transactionnelles. Plusieurs choix de conception expliquent pourquoi :

  • les attributs les plus consultés (uid, mail) sont indexés, ce qui rend leur recherche très rapide,
  • les recherches sont scopées à une portion précise de l'arbre plutôt qu'à l'ensemble de l'annuaire, ce qui réduit le coût de chaque requête,
  • le modèle de réplication privilégie de nombreuses répliques en lecture seule pour quelques nœuds maîtres en écriture — un choix cohérent avec une charge dominée par des milliers de tentatives de connexion et de recherches, contre relativement peu de créations ou modifications de comptes,
  • un schéma strict impose une structure prévisible aux données, ce qui évite le coût de jointures complexes qu'une base relationnelle devrait gérer pour un usage équivalent.

Cette asymétrie a une contrepartie : LDAP gère mal les écritures fréquentes, la contention sur les nœuds maîtres, et les transactions complexes — des scénarios pour lesquels une base de données relationnelle classique reste mieux adaptée. Ce n'est pas une faiblesse de conception, c'est une spécialisation : LDAP a été pensé pour un usage — l'identité, consultée en permanence, modifiée rarement — pas pour être une base de données généraliste.

Ce que les outils IAM modernes ajoutent, et ce qu'ils ne remplacent pas

Une question légitime se pose à ce stade : si Active Directory gère déjà les utilisateurs, l'authentification et une forme de contrôle d'accès via les groupes, pourquoi des organisations investissent-elles dans des outils IAM supplémentaires comme Okta, SailPoint ou Keycloak ?

La réponse tient à une différence de nature, pas de fonction :

Critère Approche historique (AD/LDAP seuls) Outils IAM modernes
Gestion des rôles Groupes gérés manuellement RBAC automatisé, revues d'accès périodiques
Périmètre Réseau interne, on-premise Cloud, SaaS, multi-environnements
Authentification Bind LDAP direct SSO, MFA, SAML, OpenID Connect
Session / jeton Aucun — LDAP répond juste "valide ou non" Sessions gérées, tokens signés (JWT)
Gouvernance Journaux à interpréter manuellement Audits automatisés, certifications d'accès

La ligne "session / jeton" est la plus révélatrice : LDAP ne gère ni l'un ni l'autre. Dans une architecture moderne, l'annuaire n'est presque jamais interrogé directement par une application — il se trouve derrière un Identity Provider, qui lui pose les questions bind/search en coulisses, puis émet lui-même les jetons décrits dans les articles précédents de cette série. Keycloak, par exemple, peut être configuré pour fédérer ses utilisateurs directement depuis un annuaire LDAP ou Active Directory existant : l'annuaire reste la source de vérité, Keycloak ajoute par-dessus les protocoles modernes de délégation.

Ce que cet article laisse ouvert

Un annuaire répond à "où l'identité est stockée", et LDAP répond à "comment un système l'interroge et l'authentifie localement". Mais aucun des deux ne répond à une question qui devient centrale dès qu'une organisation utilise plusieurs systèmes indépendants : comment un utilisateur authentifié dans un annuaire accède-t-il, sans se reconnecter, à une application qui ne partage pas cet annuaire — potentiellement chez un autre fournisseur, ou dans une autre organisation ? C'est le rôle de la fédération d'identité, qui fera l'objet d'un prochain article de cette série.
